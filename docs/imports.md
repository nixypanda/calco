# Imports

## Overview

Imports are handled from CLI scripts, not from a browser admin UI.

The import system has two parts:

- **Data sources pipeline** (`tools/importers/data-sources/`) for converting
  public food datasets into catalog rows via the backend import API.
- **Personal data import** (`tools/importers/personal-data/`) for importing user
  data from other apps (MyFitnessPal, etc.) via user-facing CalCo APIs.
- Backend import API for staging, validating, committing, and inspecting import
  jobs.

## Backend Flow (Data Sources Pipeline)

Import jobs are admin-only.

```text
POST /api/imports
POST /api/imports/{id}/foods
POST /api/imports/{id}/nutrients
POST /api/imports/{id}/servings
POST /api/imports/{id}/commit
GET  /api/imports/{id}
GET  /api/imports/{id}/errors
```

Staging tables:

- `staging_products`
- `staging_product_nutrients`
- `staging_product_servings`
- `import_errors`

Commit behavior:

- Upsert products by `(source, source_id)`.
- Insert/update product nutrients by canonical nutrient code.
- Insert/update servings.
- Record unresolved or invalid rows as import errors.
- Mark the import committed when done.

## Normalized Row Shapes

Food row:

```json
{
  "source": "USDA",
  "source_id": "123",
  "barcode": null,
  "name": "Rice, white, raw",
  "brand": null,
  "categories": ["grain"],
  "serving_size_g": 100,
  "row_number": 1
}
```

Nutrient row:

```json
{
  "source": "USDA",
  "source_id": "123",
  "nutrient_code": "ENERGY_KCAL",
  "amount_per_100g": 365,
  "row_number": 1
}
```

Serving row:

```json
{
  "source": "OFF",
  "source_id": "abc",
  "label": "serving",
  "quantity": 1,
  "unit": "serving",
  "grams": 30,
  "row_number": 1
}
```

## CLI: `calco-import` (Data Sources)

The recommended entrypoint is the `calco-import` CLI app under `tools/importers/data-sources/`:

```text
tools/importers/data-sources/
  calco-import                    ← executable wrapper
  src/calco_import/               ← Python package
    cli.py                        ← typer CLI, dispatch
    fetch.py                      ← download + convert per dataset
    merge.py                      ← dedup logic
    pipeline.py                   ← upload logic
    util.py                       ← shared helpers
  nutrient_mapping/
```

### Usage

```text
calco-import <command> <dataset> [options]
```

Commands:

| Command | Description |
|---------|-------------|
| `fetch`  | Download raw data + convert to normalized JSONL. |
| `merge`  | Deduplicate all fetched datasets into `merged.jsonl`. |
| `upload` | Upload a processed JSONL file to the backend API. |
| `import` | `fetch` + `upload` (full pipeline for a dataset). |

Datasets: `usda`, `off`, `ifct`, `indb`, `merged`

Options:

| Flag | Env var | Default |
|------|---------|---------|
| `--api-url` | `CALCO_API_URL` | `http://localhost:3001` |
| `--session-token` | `CALCO_SESSION_TOKEN` | Prompts interactively |
| `--data-dir` | `CALCO_DATA_DIR` | `./data` |
| `--dry-run` | — | Skip upload |

### Examples

```bash
# Fetch and convert all sources
calco-import fetch usda
calco-import fetch off
calco-import fetch ifct
calco-import fetch indb

# Merge all sources
calco-import merge

# Upload a dataset
CALCO_SESSION_TOKEN=<token> calco-import upload merged

# Full pipeline when session token is set
CALCO_SESSION_TOKEN=<token> calco-import import ifct
CALCO_SESSION_TOKEN=<token> calco-import import indb

# Full pipeline for merged (fetches all, then merges, then uploads)
CALCO_SESSION_TOKEN=<token> calco-import import merged

# Dry-run check
calco-import --dry-run fetch ifct
calco-import --dry-run fetch indb
```

## Snapshot Testing

Reference outputs generated by the legacy converters are kept in `tools/importers/data-sources/data/reference/`
(`usda_sr_legacy.jsonl`, `ifct2017.jsonl`, `indb_2024.jsonl`, `off_india.jsonl`). When making changes to
the converter pipeline, verify correctness by regenerating with the new code and
diffing against these references:

```bash
cd tools/importers/data-sources

# Generate new output in a temp dir
CALCO_DATA_DIR=/tmp/verify uv run python -m calco_import fetch usda
CALCO_DATA_DIR=/tmp/verify uv run python -m calco_import fetch indb

# Diff against reference
diff <(sort data/reference/usda_sr_legacy.jsonl) <(sort /tmp/verify/processed/usda_sr_legacy.jsonl)
diff <(sort data/reference/indb_2024.jsonl) <(sort /tmp/verify/processed/indb_2024.jsonl)
```

When the diff is clean and the changes are intentional, update the reference by
copying the new output:

```bash
cp /tmp/verify/processed/usda_sr_legacy.jsonl data/reference/
cp /tmp/verify/processed/indb_2024.jsonl data/reference/
```

The reference outputs are gitignored and managed locally. Run this for all
datasets (`usda`, `ifct`, `indb`, `off`) before and after any converter change.

## Personal Data Import (MyFitnessPal)

The MyFitnessPal importer lives at `tools/importers/personal-data/mfp_import.py`.
See `tools/importers/personal-data/README.md` for the full workflow.

### Quick reference

```bash
# Dry run (generate review CSV)
cd tools/importers/personal-data
python3 mfp_import.py food-dry-run

# Commit reviewed foods
python3 mfp_import.py food-commit \
  --input apps/mfp-data-working-cleaned.csv \
  --review apps/mfp-food-review.csv \
  --session-token <token>

# Import diary history
python3 mfp_import.py history-import \
  --input apps/mfp-data-working-cleaned.csv \
  --session-token <token>
```

### API endpoints used

```text
GET  /api/foods/search
GET  /api/foods/{id}
POST /api/foods/custom
POST /api/logs
GET  /api/logs?from=YYYY-MM-DD&to=YYYY-MM-DD
```

### Data flow

1. **Food dry-run** groups MFP rows by normalized description, suggests
   `match`/`create`/`skip`.
2. **User edits** review CSV: sets `approved=yes` and picks actions.
3. **Food commit** creates/matches foods via API, writes `mfp-food-map.json`.
4. **History import** uses the food map to create food log entries, reports
   nutrient mismatches.

## Data Loss Tradeoff

Converters intentionally project raw datasets into the current CalCo product model. Many source-specific fields are dropped, and source category strings are normalized into `categories`. This is accepted for now and tracked in [known issues](known_issues.md).

Adding fields such as ingredients or allergens is a schema/domain change, not a converter flag.
